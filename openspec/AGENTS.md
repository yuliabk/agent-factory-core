# OpenSpec Authoring Rules

- Keep one active change per bounded business outcome.
- Write `proposal.md` before `design.md`, specifications, or implementation tasks.
- Use stable requirement identifiers.
- Write normative requirements with `SHALL`.
- Add acceptance scenarios in `GIVEN / WHEN / THEN` form.
- Use `## ADDED Requirements`, `## MODIFIED Requirements`, and `## REMOVED Requirements` in change deltas.
- Map every implementation task to at least one requirement ID.
- Include failure, authorization, fallback, privacy, and observability scenarios where relevant.
- Do not mark implementation tasks complete without evidence.
- Stop for Owner approval when a decision changes scope, cost, data handling, external actions, or platform choice.
